## 1. 목적

채용 지원서에 첨부할 개인 포트폴리오 웹사이트를 만든다.

이 사이트의 핵심 명제는 **"AI로 디자인을 직접 구현할 줄 아는 디자이너(AX 디자이너)"** 이며,
사이트 자체가 그 명제의 증거물이다. 즉 **실린 내용(작업물)과 그릇(이 사이트)이 같은 주장을 해야 한다.**

세 가지를 동시에 증명한다.

1. **디자인 감각** — 절제된 에디토리얼 레이아웃, 타이포 위계, 여백 운용
2. **구현 능력** — Next.js로 직접 만들고 GitHub/Vercel로 직접 배포한 실제 URL
3. **AI 워크플로 역량** — 여러 AI 엔진을 목적에 따라 갈아 쓰는 방식, 프롬프트 설계 관점

### 이 사이트가 하지 않는 것
- 모든 작업물의 아카이브가 아니다. **선별된 대표작만** 싣는다.
- 기술 블로그가 아니다. Notes는 워크플로 인사이트에 한정한다.

## 2. 타깃 사용자

| 우선순위 | 대상 | 상황 | 이 사람이 찾는 것 | 설계 함의 |
|---|---|---|---|---|
| 1 | **채용 담당자 / 리크루터** | 지원서 링크를 클릭. **모바일**로 열 확률 높음. 체류 30초~1분 | 이 사람이 뭘 하는 사람인지, 실제로 만든 게 있는지 | Hero 한 줄로 포지셔닝 전달, 모바일 완성도, 로그인·비밀번호 없음 |
| 2 | **디자인 리드 / 실무 면접관** | 면접 전후 데스크톱으로 정독. 체류 5분 이상 | 문제 정의력, 과정, 판단 근거, 실제 산출물 품질 | Work 상세의 Problem → Process → AI Workflow → Result → Learnings |
| 3 | **동료 디자이너 / 잠재 협업자** | 소셜 공유로 유입 | 워크플로 자체, 쓸 만한 팁 | Notes 섹션, OG 이미지 |

**설계 원칙:** 1번 타깃은 *스캔*하고 2번 타깃은 *정독*한다. 홈은 스캔용으로, Work 상세는 정독용으로 설계한다.

## 5. 페이지별 상세 — 섹션 목적

각 섹션은 **"무엇을 보여주는가"가 아니라 "무엇을 납득시키는가"** 로 정의한다.

### 5.1 Home — 스캔용. 30초 안에 결론을 준다.

| # | 섹션 | 목적 (무엇을 납득시키는가) | 구성 |
|---|---|---|---|
| 1 | **Hero** | "이 사람이 뭐 하는 사람인지" 3초 안에 | 이름 + 한 줄 포지셔닝 + 서브 카피 1~2줄 |
| 2 | **AI Toolkit** | 도구 폭이 넓고, 말만 하는 게 아님 | 가로 리스트: Figma, Figma Make, Claude Code, Codex, Gemini, Grok, Antigravity, Photoshop, Illustrator |
| 3 | **Selected Work** | 결과물이 실제로 존재함 | 대표 프로젝트 카드 (큰 썸네일 또는 자동재생 영상 + 제목 + 카테고리 태그) |
| 4 | **Numbers** | 규모와 경험을 숫자로 압축 | 숫자 4개 — 값은 플레이스홀더, 사용자가 채움 |
| 5 | **Notes 미리보기** | 생각의 깊이가 있음 | 최신 글 3개 카드 |
| 6 | **Footer CTA** | 연락 행동을 유도 | 큰 문장 + 이메일 / 인스타그램 / 링크드인 |

**Numbers 항목 (초안, 값은 빈칸):**
다뤄 본 AI 엔진 수 · 직접 배포한 서비스 · 이끈 팀원 수 · 진행한 프로젝트

### 5.2 Work 목록 — 훑고 고르게 한다.

- 카드 그리드 + 필터: **전체 / UI·AI 구현 / 브랜딩·그래픽**
- 카드 요소: 썸네일(또는 영상) · 제목 · 한 줄 요약 · 카테고리 태그 · **상태 배지(완성 / 진행 중)**
- 필터는 URL에 반영(`/work?category=ui-ai`)해 공유·뒤로가기가 동작하게 한다

### 5.3 Work 상세 — 정독용. 전 프로젝트 공통 템플릿.

| # | 블록 | 목적 |
|---|---|---|
| 1 | 헤더 | 제목 · 한 줄 요약 · 역할 · 기간 · 사용 도구 |
| 2 | **Problem** | 왜 시작했는지 — 문제 정의력 증명 |
| 3 | **Process** | PRD → 디자인 시스템 → MCP로 실제 서비스 화면 참고한 와이어프레임 → Figma·AI 왕복 → 구현 |
| 4 | **AI Workflow** | 어떤 엔진을 왜 썼는지, 프롬프트 설계 포인트 — **이 사이트의 차별점** |
| 5 | **Result** | 최종 화면·영상·실제 링크 |
| 6 | **Learnings** | 배운 점 2~3줄 — 성찰 능력 |
| 7 | 이전/다음 이동 | 이탈 방지 |

> 브랜딩·그래픽 프로젝트는 4번(AI Workflow)이 비어 있을 수 있다. **빈 블록은 렌더링하지 않는다.**

### 5.4 About — 사람으로서 신뢰를 준다.

- 짧은 자기소개
- **협업 방식:** 명확한 언어로 전달하고 상대의 핵심을 정확히 이해하는 것 (사람에게도, AI에게도) — AX 디자이너 명제와 직결되는 문단
- **경험 타임라인**
  - 캐나다 어학연수 (8학년 1학기, 9학년 이수)
  - 제품 디자인 동아리 팀 리딩 (약 30명, 6개 부서): 청소기 디자인, LA 올림픽 굿즈 브랜딩
  - 졸업전시 컨셉팀장 (6명): 컨셉·스토리·로고·타이포·컬러·굿즈·도록·영상·포스터 총괄
  - 멘토링 특강 "남들과 다른 디자이너 되기 TIP"
- 사용 도구와 활용 수준

### 5.5 Notes — 생각을 판다.

초기 글 3개, 제목과 요약만 플레이스홀더:

1. "AI 엔진마다 성격이 다르다: Claude Code, Codex, Gemini, Grok 비교"
2. "Grok Bot으로 AI 팀원 꾸리기"
3. "PRD부터 배포까지, 디자이너의 바이브 코딩 워크플로"

### 5.6 Contact — 연락 장벽을 없앤다.

- 이메일 · 소셜 링크 (인스타그램, 링크드인)
- 이력서 PDF 다운로드 버튼 — **파일은 추후 추가**, 없을 때 처리 방식은 Q9 참조

## 6. 콘텐츠 모델

콘텐츠는 **한 곳**에서 관리한다. 프로젝트를 추가할 때 컴포넌트 코드를 고치지 않는 것이 성공 기준 S6이다.

### 6.1 프로젝트 스키마

```
slug       string                 URL 경로
title      string                 제목
summary    string                 한 줄 요약
category   "ui-ai" | "branding"   카테고리
status     "done" | "wip"         완성 / 진행 중
role       string                 역할
period     string                 기간
tools      string[]               사용 도구
thumbnail  string                 public/projects/[slug]/ 기준 경로
video      string?                카드·상세 영상 (선택)
links      { label, url }[]       실제 서비스 링크 등 (선택)
body       Problem / Process / AI Workflow / Result / Learnings
```

### 6.2 초기 프로젝트 6건 (내용은 플레이스홀더, 구조만 완성)

| slug | 제목 | 카테고리 | 상태 | 비고 |
|---|---|---|---|---|
| `todo-tool` | 업무 생산성 To-do 툴 | UI·AI 구현 | 완성 | 사용자 데이터 서버 구축, 앱 배포, Codex 사용. 실제 링크 미정 |
| `google-maps` | Google Maps 개선 | UI·AI 구현 | 완성 | 인터랙티브 애니메이션 → 영상 인코딩. **카드에 영상 사용** |
| `co-us` | CO-US | UI·AI 구현 | 진행 중 | 과정 중심으로 서술 |
| (미정) | 3학년 과제 | 미정 | 완성 | 내용 추후. 임시 slug 제안: `year3-project` |
| `grad-exhibition` | 졸업전시 브랜딩 | 브랜딩·그래픽 | 미정 | 로고·타이포·포스터·굿즈·도록 |

## 7. 디자인 방향 (요약 — 상세는 2단계 `docs/DESIGN_SYSTEM.md`)

- **레퍼런스:** Framer 템플릿 "Kiban" — **분위기와 구조만** 참고. 코드·이미지·문구 복사 금지, 레이아웃은 새로 설계
- **톤:** 순백 배경의 미니멀 에디토리얼. 넓은 여백, 강한 타이포 위계
- **컬러:** 배경 `#FFFFFF` / 보조 면 `#F5F5F5` / 본문 `#111111` / 보조 텍스트 `#6B6B6B` / 구분선 `#E5E5E5`
- **포인트 컬러:** **1개만.** 링크, "진행 중" 배지, 호버에만 사용 — 후보는 12번 Q1 참조
- **타이포:** 헤드라인 데스크톱 64~96px, 본문 16~18px, 줄간격 넉넉하게. **크기 단계 6개 이내**
- **그리드:** 데스크톱 12컬럼 / 최대 폭 1200~1280px / 모바일 좌우 20px
- **모션:** 스크롤 페이드업, 카드 호버 시 이미지 미세 확대. **과한 패럴랙스 금지**
- **라이트 모드만** (다크 모드 미제공)

모든 값은 **CSS 변수 토큰**으로 정의하고, 컴포넌트는 토큰만 참조한다 (성공 기준 M6).

## 9. 배포 및 버전 관리

### 9.1 버전 관리

- `git init` 완료 (기본 브랜치 `main`)
- **각 단계 종료 시 의미 있는 메시지로 커밋** (예: `docs: PRD 초안 작성`, `feat: 프로젝트 카드 컴포넌트`)
- `.gitignore` 확인 완료: `node_modules` · `.env*` · `.next` · `.vercel` **모두 포함됨**
- API 키·개인정보를 코드에 넣지 않는다

### 9.2 배포 (5단계에서 실행)

1. `npm run build` 무에러 통과 확인
2. GitHub 저장소 생성 후 푸시 — 이름 `[영문이름]-portfolio`, **Public**
   - **현재 이 PC에 `gh` CLI가 설치되어 있지 않음.** 설치하거나, 웹에서 저장소를 만들고 푸시하는 절차를 안내한다 (Q7)
3. **Vercel 연결은 사용자가 직접 수행** — vercel.com → Add New → Project → 저장소 선택 → Deploy
   - 예상 설정: Framework `Next.js` 자동 감지, Build Command `npm run build`, 환경 변수 불필요
4. 배포 후 **시크릿 창**에서 `프로젝트이름.vercel.app` 접속 → 로그인 없이 열리는지 확인 (성공 기준 M3)
5. 이후 `main` 브랜치 푸시 시 자동 재배포 유지
